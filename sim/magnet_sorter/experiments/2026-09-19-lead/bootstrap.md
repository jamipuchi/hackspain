# Headless MuJoCo bootstrap — 2026-09-19

Phase A of the adaptive-routing work: provision a root-free headless renderer in the worker
container and prove the magnet sorter scene actually renders. No paid model runs were made.

**Result: the environment is unblocked. `MUJOCO_GL=osmesa` works; `egl` does not.**

## Quick start

```bash
bash sim/magnet_sorter/experiments/2026-09-19-lead/bootstrap.sh
source sim/magnet_sorter/experiments/2026-09-19-lead/env.sh
```

`bootstrap.sh` is idempotent and self-verifying: it provisions, renders both cameras, asserts
the frames are not blank, and runs the focused suite under both build configs. A clean run from
an empty prefix takes about 8 seconds. `env.sh` is generated by the script and is gitignored —
regenerate it rather than committing it.

## Environment variables

```bash

export PYOPENGL_PLATFORM=osmesa

```

## What is installed, and where

Default prefix: `/workspace/shared/misc/<agent-id>/toolchains`.

`/workspace/shared` itself is owned by root and is not writable. `/workspace/shared/misc/<agent-id>/`
*is* worker-owned, and every agent runs as the same uid (1001, `worker`), so anything placed there is
readable and writable by the whole swarm. That is the closest thing to a shared prefix available
without root. Override it with `SORTER_TOOLCHAIN_PREFIX`.

| What | Where | How |
| --- | --- | --- |
| OSMesa + llvmpipe + libGL stack (39 Ubuntu noble .debs) | `$PREFIX/osmesa/usr/lib/x86_64-linux-gnu` | `apt-get download` then `dpkg-deb -x` |
| apt state (redirected so no root-owned path is touched) | `$PREFIX/apt` | `APT_CONFIG` with `Dir::State::lists` and `Dir::Cache` pointed into the prefix |
| Python venv | `contracts/.venv` | host `python3` (3.12.3) |

Key packages: `libosmesa6` (25.1.7) supplies `libOSMesa.so.8` and the llvmpipe software
rasteriser, which needs no GPU and no `/dev/dri`. `libllvm17t64` is llvmpipe's JIT backend.
The `libgl1`/`libglx0`/`libglvnd0` group is there only because OpenCV dlopens `libGL.so.1` at
import time — MuJoCo's osmesa path never uses it. Without it, `test_agent_brain.py` fails to
import with `ImportError: libGL.so.1: cannot open shared object file`.

`dpkg-deb -x` unpacks without touching the dpkg database, which is why none of this needs root.

## Renderer: osmesa works, egl does not

`MUJOCO_GL=egl` fails, as expected with no `/dev/dri`:

```
ImportError: Cannot initialize a EGL device display. This likely means that your EGL driver
does not support the PLATFORM_DEVICE extension, which is required for creating a headless
rendering context.
```

This was tested against a conda-forge `mesalib` 26.2.1 prefix that did provide `libEGL.so.1`,
`libEGL_mesa.so.0` and a `swrast_dri.so`, so the failure is not a missing library — that Mesa
build simply exposes no EGL device to enumerate. HANDOFF line 144 suggests `egl`; it should say
`osmesa` for this container.

The micromamba/conda-forge route was tried first per the plan. It is a dead end here for two
reasons: current `mesalib` ships no `libOSMesa` at all (there is no `osmesa` package on
conda-forge), and its EGL cannot produce a headless device. It also costs ~1.6 GB against
140 MB for the .deb route. `bootstrap.sh` therefore implements only the .deb path.

## Blocking hazard for the experiment run: one Renderer per process

**`run_demo.py --cameras A,B` will produce a garbage frame for one of the two cameras under
OSMesa.** This is not a hypothetical; it is what happened on the first render attempt:

```
cam_A: mean=99.163 std=40.195     <- correct scene
cam_B: mean=2.036  std=18.400     <- uninitialised framebuffer, visually black with colour speckle
```

Cause: `camera.py:MujocoPhoneCamera.__init__` constructs its own `mujoco.Renderer`, and
`run_demo.py:273` constructs one `MujocoPhoneCamera` per camera name. Each `Renderer` creates its
own OSMesa context, and under OSMesa the earlier context then renders uninitialised memory.
Switching to a single shared `Renderer` for both cameras fixed it immediately, with no other
change:

```
shared-ctx cam_A: mean=99.163 std=40.195
shared-ctx cam_B: mean=95.514 std=47.387
```

Both cameras are 960x1280 in `scene_def.CAMERAS`, so one `Renderer` covers both. Whoever runs the
paid experiment must fix this before trusting any two-camera result — a silently black cam B would
poison the vision comparison and burn budget on garbage input. The fix belongs in `camera.py`:
share one `Renderer` across `MujocoPhoneCamera` instances (module-level cache keyed by
`(model, height, width)`) rather than creating one per camera.

Note that `mean` alone does not catch this — `std` or a pixel-variance check is the reliable
blank-frame test. `bootstrap.sh` asserts `std >= 25`.

## Deviations from the plan

- Prefix is `/workspace/shared/misc/<agent-id>/toolchains`, not `/workspace/shared/toolchains`,
  because the latter is root-owned and unwritable. It is still shared (see above).
- Python is the host 3.12.3, not 3.14. HANDOFF line 103 makes 3.14 conditional on availability,
  and everything passes on 3.12.3. No source build was attempted.
- Only the .deb path is in `bootstrap.sh`; the micromamba path was tried, failed, and is
  documented above rather than shipped.
